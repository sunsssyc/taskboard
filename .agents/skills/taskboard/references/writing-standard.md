# 看板文案标准

在新增、编辑或审查看板文案时使用本标准。目标是让接手者在首屏内分清：现在是什么状态、下一步做什么、依据是什么、哪些信息已经过期。

## 固定字段标签

不要为同一种信息临时发明标签。

| 对象 | 固定标签 |
|---|---|
| 需求简介 | 无标签，直接写当前状态和主线 |
| 任务正文 | `目标`、`当前状态`、`待办`、按需使用 `决策待定` |
| finding | `影响`、`证据`、`决定`、按需使用 `边界` |
| risk | `影响`、`触发条件`、`缓解措施`、按需使用 `退出条件` |
| link | `用途`、按需使用 `范围` |

标签统一写成 Markdown 加粗段名，例如 `**当前状态**：`。同一事实只放在一个字段中。

## 统一状态用语

交付状态必须写清边界，禁止用“完成”“已发版”“已上线”代替具体阶段：

1. `本地生成`：产物只存在本地。
2. `已提交`：改动进入本地 Git 提交。
3. `已推送`：提交已进入远端分支。
4. `已发布到 staging`：远端暂存产物可用。
5. `已发布到 production`：生产指针或制品已切换。
6. `已部署`：运行环境已加载目标代码或产物。
7. `线上已验证`：真实链路和结果已核验。

只写已被证据确认的最高阶段。例如 S3 仅通过预览时写“本地发版物已冻结，S3 尚未写入”，不能写“release 完成”。

## 需求名称与简介

- 展示名称只保留一个主名称，优先使用中文；英文 key、仓库名和版本号放在各自字段中。
- 简介只写当前事实、当前主线和硬约束，控制在首屏一到两行。
- 发版、切版、主线或统摄性结论变化时，直接改写简介；不要追加更新日志。
- 只保留会改变当前决策的引用，不列证据清单。

推荐句式：

```markdown
生产仍运行 v3.2，注册时间缺失用户继续豁免。v4 本地发版物已冻结，当前待生产发布、部署和线上验收。
```

## 任务文案

### 标题

- 使用“动词 + 一个交付物”。
- 一个标题只承诺一件事；出现加号、并列逗号或冒号后仍有动作时，优先拆任务。
- 版本、阈值、提交号和实验结果放入“当前状态”，不塞进标题。
- 不写“收尾杂项”“优化一下”“处理相关问题”等无法验收的表达。

好：`部署并验收 v4 注册风控模型`

差：`v4 组合包：类目修复 + 阈值重钉 + 发布监控`

### 正文

```markdown
**目标**：说明交付物及其业务目的。

**当前状态**：只写最新版本、已完成边界和剩余阻塞。

**待办**：
- ⬜ 动词开头，一行一件事
- ✅ 已完成项保留到任务结束

**决策待定**：
- 问题：可选方案、关键取舍和推荐项
```

- 正文只保留当前口径，不叙述任务如何演化，也不写“拆自 #N”“本轮先不做旧版本”等出处。
- 每段不超过 5 个清单项；超过时拆任务，或把实验细节下沉到 finding。
- `✅`、`⬜` 只用于“待办”清单。不要用箭头把多个步骤串成一行。
- 提交 SHA、完整报告名、日志和大表放入 finding 或 link；任务只引用必要的 `[ID]`。
- `--accept` 单独写可检查的完成条件，正文不重复验收条件。

### 状态、负责人和依赖

- 有已完成清单项或正在执行的工作时，任务状态应为 `active`，不能仍为 `todo`。
- 每个未完成任务必须有 `我`、`你` 或 `双方`负责人。
- 外部授权或人工操作使用 `waiting`；前置任务未完成时记录依赖，不在正文里描述“等 #N”。
- 已完成的历史监控窗口及时 `done`；已失去意义的候选任务及时 `drop`。

## finding 文案

### 标题与 metric

- 标题只写一个当前判断，不写推演过程，不把正文或多组指标塞进标题。
- `metric` 只放一到两组最能支撑判断的数字，用 `·` 分隔；提交 SHA 不是 metric。
- 数字必须带对象和口径，例如 `注册时间缺失豁免 82.34%`，不能只写 `0.8234`。

好：`v4r6 在 0.20 阈值下优于 v4r5`

差：`交叉考卷定夺：v4r5 低阈值更好但 v4r6 在 0.20 持平且解决过期快照——定 v4r6@0.20`

### 正文

```markdown
**影响**：该判断会改变哪项决策。

- `证据`：一条证据只支撑一件事。
- `决定`：后续采用的明确口径。
- `边界`：仍未验证或不在本次范围内的部分。
```

- 影响段不超过两句；机制和实验过程放到证据。
- 一条证据不使用分号串联多组实验。
- 同一句最多引用两条记录；完整数据通过 `board link` 给入口。
- 标题不得包含换行；正文不得误写入标题字段。

## risk 与 link 文案

- risk 标题写一个仍可能发生的结果，不把“已修”“待验证”与风险本身并列在标题中。
- risk 正文必须说明影响和触发条件；已有缓解方案时写明退出条件。
- link 标题使用稳定、可识别的文件或入口名称；正文说明用途，不复述文件内容。

## 分类与生命周期

- 同一需求复用 2～6 个稳定主题。分类描述领域，不描述版本、日期、状态或单条事件。
- 新记录先运行 `board notes -p <key>`，复用已有分类；同义分类合并。
- 核心判断失效时使用 `supersede`，并让新结论完整表达当前口径。
- 判断仍成立但已经执行完、不再影响下一步时使用 `settle`。
- 只记录历史过程、已失效分支状态或旧候选参数的记录，不得继续留在活跃结论中。

## 可读性约束

- 中文叙述使用中文标点；字段名、函数、命令、路径和不可翻译的模型术语使用反引号。
- 首次出现的必要英文术语用“中文含义（英文术语）”，后续只用一种叫法。
- 减少括号和破折号；补充信息能独立成句时直接拆句。
- 每个段落只回答一个问题，先给结论，再给原因。
- 不粘贴原始 HTML、整段日志、图片或复杂嵌套列表。

## 写入前检查

- 需求简介是否仍是当前事实。
- 标题是否只有一个动作或判断，且没有换行。
- 状态词是否明确区分本地、提交、推送、发布、部署和线上验证。
- 任务是否具备目标、当前状态、待办、负责人和验收条件。
- finding 的 metric 是否不超过两组，正文是否给出决定和边界。
- 是否该沉淀或推翻旧记录，而不是继续累加“当前结论”。
- 分类是否仍控制在 2～6 个稳定主题。

## CLI 多行参数

CLI 参数必须包含真实换行。bash/zsh 使用 ANSI-C 单引号：

```bash
board finding "结论" --body $'**影响**：一句话。\n\n- `证据`：已验证'
```

不要把 `\n` 放进普通双引号；shell 不会将其展开，正文中的反引号还可能触发命令替换。
