# Taskboard：把 Agent 产出变成可分诊、可对齐的审查队列

> 调研日期：2026-08-27
> 状态：A、B、C、E 层已实现（#35、#38、#41、#39）；D 待定去留；#40 的 link 迁移待做

## 问题

两个痛点，是同一件事的两面：**读不完**是量的问题，**读不懂**是质的问题。

### 一、读不完

Agent 写代码的速度已经超过人读代码的速度，人的时间只够读一部分，但今天**没有依据决定读哪一部分**，于是要么全读（读不完）要么随便读（漏关键改动）。

实测（`taskboard` 仓库近 14 天，40 个提交）：

- 单次提交改动行数中位数 171、p90 1007、最大 8901
- 08-24 一天 7 个提交共 12998 行
- 122 个任务里 `pr` 字段填写数为 **0** —— 审查不发生在 GitHub PR 上，发生在本地提交上

看板已经记了"为什么改"（任务 detail、验收条件、finding），git 记了"改了什么"（diff），**两者之间没有可信映射**。现有的那一条映射是坏的：

- `board done` 只记一个 `git_head_sha()`，取的是 **CLI 进程的 cwd**，不是任务关联仓库
- 只有终点没有起点，无法还原区间
- 90 条带 commit 的 done 事件只落在 **56 个不同 SHA** 上，其中 48 条与别的任务共用同一个 SHA。实例：`#30` 与 `#31` 都记 `043a3ef`，`#27` 记的 `9e144b7` 是另一个任务的提交
- 另有 17 条 done 事件完全没有 commit（在仓库外执行 `board done`）

推断：这不是"看板缺一个审查页面"，而是**任务与它产出的代码之间缺一层数据**。没有这层，任何排序、分诊、审查进度都建立在猜测上。A 层已补上这层。

### 二、读不懂

Agent 的知识面比人宽。人读 agent 的策略和代码成本高，往往不是因为代码难，而是**它依赖人没有的概念**——读 diff 只能看到结果，看不到选它的理由。

业界叫 **comprehension debt**：已交付的代码和真正有人理解的代码之间的差额。它比技术债危险，因为技术债会通过构建变慢、依赖纠缠自己冒出来，comprehension debt 只制造虚假信心，速度指标测不到。

以下为转述的外部证据，非本项目实测：一个 52 人 RCT 中，AI 辅助组完成时间与对照组相当，但后续理解测验低 17 个百分点（50% vs 67%），降幅最大的是调试；Sonar 调查中 96% 的开发者不完全信任 AI 生成代码的正确性，只有 48% 每次提交前都检查，38% 认为审 AI 代码比审同事代码更费劲。帮人复核 AI 产出的工具类别学术上叫 **co-audit**，其原则包括：解释落在用户已有概念上、帮用户决定优先查哪部分、记录哪些已查过。

本项目实测的一个具体形态：`coinex_translate_server` 同时服务 `kyc-image-precheck`（23 条
finding）与 `gemini-37-flash-upgrade`（35 条 finding）两个需求。同一套"思考参数/thinking
level 契约"在两边各记各的——前者有「Qwen3.8 思考 A/B 参数口径」，后者有「thinking 分类已
重构为模型能力 profile」。后者是对同一段代码的重构，理应让前者失效，但两条记录互相看不见。

推断：只做分诊（C 层）只解决第一个痛点。把该读的挑出来之后，人还是读不动。

## 方案

五层，后面依赖前面。

### A. 任务提交区间（已实现，任务 #35）

新表 `task_commits(task_id, repository_id, base_sha, base_at, head_sha, head_at)`：

- `todo→active` 时对任务的**每个**关联仓库分别取 HEAD 写 `base_sha`
- `→done` 时同样逐仓库取 HEAD 写 `head_sha`
- 起点只记第一次，任务退回重做后区间仍覆盖全部改动

取 SHA 集中在 `taskboard/gitref.py`，不再按 cwd 取。两端齐全才算完整区间；sha 被 rebase/squash 掉时明说失效，不退化成错误的 diff。历史已完成任务不补录。

### B. `board review <ref>`：单任务审查包（已实现，任务 #38）

一屏内给出判断"这次改动是否兑现了当初的意图"所需的全部材料：

- 任务标题、detail（为什么做）、验收条件
- 逐仓库 diffstat 与变更文件清单（按改动行数排序）
- 命中的概念锚点与关键文件
- 区间内新增或被推翻的 finding

不渲染 diff 本身。`board review <ref> --diff` 直接 exec `git diff base..head`，渲染交给 git/delta。

### C. `board review --queue`：按风险排序，不按时间（已实现，任务 #41）

排序主信号是**是否引入未对齐概念**（见 E 层），不是改动规模。理由：800 行但全落在已对齐概念内的改动扫一眼就够；30 行但引入一个新调度语义的改动必须精读。规模只是次级信号。

完整信号，全部由现有数据算出，不需要人额外打标：

| 信号 | 数据来源 | 权重 |
| --- | --- | --- |
| 引入未对齐概念 | 任务提出的概念（`notes.task_id`）+ 区间动过的锚点 | 主 |
| 触碰关键文件 | `note_files`（32 条 link 迁移后） | 主 |
| 闸门任务 | `tasks.gate` | 次 |
| 期间推翻过结论 | `note_superseded` 事件（现存 91 条） | 次 |
| 改动规模 | A 层区间 + `git diff --shortstat` | 次 |
| 跨仓库 / 无验收条件 | `task_repositories` / `tasks.accept` | 次 |

「引入未对齐概念」和「期间推翻过结论」是本项目独有的信号，通用代码审查工具拿不到——这是看板做这件事的正当理由。

输出分三档并附一行理由：**必须先对齐 / 精读 / 可跳过**。默认只打印今天该读的前 N 条，不打印全量列表——全量列表本身就是过载的一部分。

### E. 概念对齐（已实现，任务 #39）

**对齐的单位是概念，不是任务。** 挂在任务上，每个任务都要重付一次理解成本，和现在读 diff 一样贵；挂在概念上才摊薄——一个概念对齐一次，后面几十个任务都受益。

**概念就是 finding 的一种。** 复用 `notes`，新增 `kind='concept'`。理由：[25] 已确立 finding 机制的价值高于任务管理本身；概念是"人已判定的事实"，语义一致；`supersede` 天然承载"这个概念被新方案推翻"。不新增记录类型 = 不新增噪音类型。

**但概念的归属是仓库，不是需求。** `finding`/`risk` 记的是推进某个目标时做的判断，属于需求；概念记的是这套代码是怎么回事，属于仓库。今天两者没被区分，只因为绝大多数仓库恰好 1:1 对应一个需求——上面 `coinex_translate_server` 的例子说明这个前提已经不成立。

按需求存会必然发散：同一个概念在两个需求下各存一份，同一次文件改动让 A 转 `stale` 而 B 仍显示已对齐，两份记录越走越远。按仓库存则三件事自动一致——锚点 `note_files` 本来就是 `(repository_id, path)`；失效判定按仓库文件算；对齐状态跟着概念走，人对齐一次，在所有关联该仓库的需求下都生效。摊薄是这个功能的全部价值，而需求边界对代码来说是任意的。

**三层递进，人读到够为止：**

1. 一句话：这是什么、解决什么问题
2. 为什么选它、替代方案为何不用 —— agent 最容易跳过、对人最有价值的一层
3. 代码坐标：文件 + 关键函数，只给坐标不贴代码

每层有硬长度上限。上限本身就是防过载机制：**概念卡必须比它解释的改动短**，否则它就是第二堵墙。

**agent 提，人裁。** 三种回应：认可 → 已对齐；追问 → agent 用 `board concept-edit` 补充（桌面端复用 #33 的派发链路）；否决 → 记录理由（"这不是新概念"、"方案本身不对"）。改了措辞自动退回待对齐——人当初认的是旧那句话。

**两种作用域。** 带代码锚点的归仓库，锚点动了会 `stale`；方法论与领域惯例这类不挂在某段代码上的归需求，不随代码失效。强行给方法论概念挑一个仓库会让归属变成掷骰子——`reg-calibration` 关联 3 个仓库，"时代误伤的定义"挂在哪个都不对。

**每个任务最多 3 个新概念。** 硬限制。agent 认为一个任务需要更多新概念时，这本身是信号：任务太大，或方案太聪明。把概念数量变成复杂度警报。

**对齐锚在提交上。** `notes.aligned_at` + `notes.aligned_commit`。之后锚点被改动、且提交晚于 `aligned_commit` → 状态转 `stale`。区分 `stale` 与从未对齐，因为两者要读的量不同。

**判定粒度必须到函数。** 实测 `taskboard/store.py` 在最近 30 个提交里被碰 13 次：按文件判会让锚在它上面的概念每两个提交失效一次，几轮之后人就闭着眼按确认——这正是「对齐沦为橡皮图章」那条风险的实现路径。带 `symbol` 的锚点用 `git log -L :symbol:path` 按函数判；git 认不出函数边界时（语言没有 diff 驱动、函数被删或改名）退回按文件，宁可多提醒也不漏报。

**新表 `note_files(note_id, repository_id, path, symbol)`。** 概念要能算失效就必须有代码锚点。顺带修一个现存问题：`link` 记录今天把路径塞在标题里（32 条里只有 17 条看着像路径），C 层的"触碰关键文件"信号没法可靠 join。`note_files` 同时服务 `link` 与 `concept`。

**对齐状态是双向的。** 它不只是人的复选框，也是给 agent 的指令：已对齐的概念可以直接用术语、不铺垫；未对齐的必须先解释。`board notes` 今天说的是"别重新推演"，对齐状态让它进一步变成"别重新解释"——这直接压缩 agent 的输出长度，也就是过载的源头。

**只有人能标已对齐**，不给 agent 代记的逃生口。

### D. 审查状态显式化（待定去留）

`done` 不等于 `reviewed`。`board reviewed <ref>` 与 `board review --skip <ref> --reason "..."`，把"我没看"变成一条可回溯的记录。

E 层落地后这一层可能变得多余：概念对齐本身就是人做过判断的证据，再加一个任务级复选框可能只是多敲一次键盘。等 C+E 用一段时间再决定。

## 约束与取舍

- finding [24]「一个人 + 一个 AI」：不做 approve/request-changes、不做 reviewer 分配、不做评论线程、不做审查耗时图表。
- 不替代 git/GitHub：不渲染 diff、不做行内评论。看板只回答「读哪些、什么顺序、读懂了没有」。
- 不把 AI 自动审查放进默认路径。再加一个 Agent 的输出会加重而不是减轻过载。
- **最大风险：概念卡变成新的话术垃圾。** 缓解是三层长度上限 + 每任务 1–2 条上限 + 人可否决并记录理由。上线一段时间后若否决率高于认可率，说明粒度或必要性判断错了，砍掉重做。
- **第二风险：对齐沦为橡皮图章。** 判据很硬——如果 C 层不消费对齐状态，这个功能就是空转。所以 E 必须和 C 一起上，不能单独先做。
- 概念粒度谁定没有先验答案：先让 agent 提、人合并拆分，用一段时间看它自然收敛到什么量级，不预设规则。
- 区间依赖 SHA 可达，rebase/squash 后失效，见 A 层处理办法。

## 验收

- B：`board review <ref>` 一屏输出不超过 40 行；跨仓库任务逐仓库分节
- C：给定一天的产出，队列前 3 条覆盖当天全部「引入未对齐概念或触碰关键文件」的改动
- E：概念卡三层齐全且各层不超上限；锚点文件被改动后自动转 `stale`；已对齐概念在新会话里 agent 不再重复解释（人工判读）；否决率可从 `board log` 查出
- C+E 合起来：人实际读的比例从「全部或随机」变成一个可陈述的数字

## 前置决策

已定（2026-08-27）：

- **概念的载体**：`notes` 新增 `kind='concept'`，不另起表——否则 CLI、渲染、搜索、supersede 四套逻辑要各写两遍。
- **归属与共享**：概念归属仓库，同一仓库下的概念在所有关联需求间共享，对齐一次处处生效。
- **每任务概念条数上限**：3，超出要 agent 说明理由。

待定：

- **跨需求展示规则**：`board notes -p X` 是把 X 关联仓库的全部概念平铺，还是只列本需求任务touch 过的？建议先平铺，量大了再收。不定的后果是同一屏里混进另一个需求的上下文，可能反而加重阅读负担。
- **失效后的状态**：转 `stale` 还是退回未对齐？建议 `stale`。不定的后果是队列无法区分"重新确认一下"和"从头解释一遍"，两者要读的量差一个量级。
