# Taskboard：从任务状态持久化到跨项目工作流

> 讨论整理日期：2026-08-23
> 状态：产品方向已形成共识，第一阶段语义与仓库关联已实现

## 一句话总结

把进度、结论和下一步都记到看板里，这样不管换了哪个 Agent、开了几个新对话，都能少走回头路，接着把事情往前推。

## 1. 核心认识：持久化的不是 Agent，而是任务状态

这次讨论最重要的修正是：后续恢复工作时，通常仍然是一个新的 Agent 实例在接手，并不存在真正连续的“同一个 Agent”。

因此，Taskboard 的价值不是维持 Agent 身份，而是把工作状态从对话中剥离出来，保存在独立、可恢复、可检查的系统中。Agent 可以更换，对话可以中断或压缩，但任务本身仍然保留：

- 当前目标与范围；
- 已完成进度；
- 已确认结论；
- 遗留风险；
- 依赖和阻塞关系；
- 下一步行动；
- 验收条件与交付证据。

这种设计降低的是换 Agent、换对话和上下文压缩后的交接成本。

参考背景：[Codex-maxxing：Durable Threads 与 Memory](https://jxnl.github.io/blog/writing/2026/05/10/codex-maxxing/#durable-threads)

## 2. 为什么要把状态放到对话之外

将任务状态沉淀到看板，主要带来以下价值：

1. **可恢复**：线程结束或上下文失真后，可以根据看板继续工作。
2. **可审查**：用户可以直接检查 Agent 记录的目标、结论和状态。
3. **可纠偏**：执行路径发生变化时，可以判断目标和范围是否漂移。
4. **可交接**：不同 Agent、不同仓库和未来的自己都能接手。
5. **减少重复推演**：已确认的 finding 不必在新对话中重新调查。
6. **降低上下文负担**：新对话只需要读取当前有效状态，而不是重放全部历史。

但外部系统必须持续更新。否则只会把“过时的聊天记录”替换成“过时的看板”。

## 3. Agent 推进任务时的控制问题

目前的主要不安并不是任务没有被记录，而是 Agent 可能同时承担：

- 拆解任务；
- 选择执行路径；
- 调整范围；
- 判断自己是否完成。

如果这些权力没有边界，用户看到的只是不断变化的任务节点，难以判断目标是否已经漂移。

解决办法不是把 Agent 的每一步操作都拆成节点，而是把看板作为任务的**控制面**，明确谁可以决定什么。

### 3.1 三层控制结构

#### 目标契约：由用户控制

- 最终要解决什么；
- 明确不做什么；
- 不可突破的业务和技术约束；
- 可以检查的验收标准。

Agent 可以提出修改建议，但不能自行改变目标契约。

#### 执行路径：由 Agent 控制

- 调研顺序；
- 代码修改步骤；
- 测试和验证方式；
- 在既定范围内的实现调整。

这些低层步骤不需要全部进入正式看板节点。

#### 决策闸门：由用户确认

遇到下列情况时，Agent 应停止推进并等待人工决定：

- 扩大任务范围；
- 改变业务语义或架构；
- 执行删除、发布、迁移等难以回滚的操作；
- 原验收条件无法满足；
- 出现多个差异明显且影响较大的方案。

### 3.2 节点应该记录什么

任务节点记录的是**承诺和控制点**，不是 Agent 的完整思考过程。

用户只需能够随时回答四个问题：

1. 当前目标有没有漂移？
2. Agent 被允许自主决定到什么程度？
3. 下一个需要人工介入的闸门是什么？
4. Agent 声称完成时提供了什么客观证据？

现有的 `--accept`、`--gate`、`board wait`、`board done`、`finding`、`risk` 和 `link` 已经可以承担大部分控制职责。

重要任务可以拆成“Agent 实现完成”和“用户验收通过”两个节点。后续交付依赖人工验收节点，避免 Agent 自我认证后一路推进。

## 4. 左侧导航应该按什么维度组织

已经形成的共识是：**左侧应按需求或长期工作流组织，而不是按代码仓库，也不是按每个原子任务组织。**

原因是人和 Agent 真正持续推进的是一个需要解决的问题，代码仓库只是实现这个目标时使用的资源。一个需求完全可能同时涉及 Backend、Admin 前端、反欺诈服务或其他仓库。

建议的信息层级为：

```text
左侧：需求／工作流
  └─ 中间：该需求下的执行任务
       └─ 任务关联的仓库、分支、PR、commit 和验证证据
```

例如：

```text
注册模型时代校准
  coinex_backend · coinex_anti_fraud_service · coinex_admin_frontend
  ▸ 发布导出采样策略
  · 按名单补录事实
  · 配比抽样与概率校准
```

### 4.1 为什么不按仓库作为一级导航

- 一个业务需求经常跨多个仓库；
- 按仓库拆开后，同一目标的进度、依赖和结论会被割裂；
- 新 Agent 接手时需要先恢复“为什么做”，而不是先选择“在哪个仓库做”；
- 用户关心的是需求是否完成，而不只是某个仓库是否发生了修改。

仓库仍然重要，但更适合作为：

- 需求和任务上的标签；
- 全局筛选条件；
- 代码坐标；
- branch、PR、commit 和测试证据的归属。

### 4.2 为什么不让每个原子任务进入左侧

左侧承担的是跨对话恢复工作流的导航职责。如果每个小任务都成为一级节点，很快会退化成一份密集的 TODO 清单。

只有具备以下特征的事项，才适合成为左侧一级节点：

- 有独立且稳定的目标；
- 包含多个执行步骤；
- 可能跨多个对话推进；
- 可能涉及多个仓库；
- 需要沉淀长期结论、风险或人工闸门。

## 5. 建议的数据模型方向

当前模型中的 `project` 同时承载了“工作流”和“Git 仓库”两种含义，并且只关联一个 `repo`。当一个需求跨多个仓库时，这个模型会产生歧义，完成任务时也无法完整记录多个仓库的交付证据。

建议逐步拆分为：

```text
workstream
  ├─ tasks
  ├─ findings / risks / links
  └─ repositories（多对多）

task
  └─ repository artifacts
       ├─ branch
       ├─ PR
       ├─ commit
       └─ validation evidence
```

- `workstream`：表示需求、目标或长期工作流，是左侧一级导航。
- `task`：表示可以执行和验收的具体动作。
- `repository`：表示代码仓库，是可复用的独立实体。
- `workstream_repository`：记录需求涉及哪些仓库。
- `task repository artifacts`：记录每个任务在不同仓库中的实际交付物和证据。

为了降低迁移成本，内部表名可以暂时保留 `projects`，先统一产品语义和界面文案；确认使用方式稳定后，再决定是否迁移数据库结构。

## 6. 左侧栏的建议呈现

每个工作流节点只展示帮助恢复上下文的信息：

- 工作流名称和一句话目标；
- 总体进度；
- 当前进行中或下一项可执行任务；
- 是否存在人工闸门；
- 涉及仓库的简短标签；
- 是否存在未处理风险。

仓库维度可以保留为顶部筛选器，例如“只看涉及 `coinex_backend` 的工作流”，但不与工作流争夺一级导航位置。

## 7. 当前已确认与尚待验证

### 已确认方向

- 持久化的是任务状态，不是 Agent 身份。
- 看板是不同 Agent 和不同对话之间的任务状态来源。
- 用户控制目标契约和关键闸门，Agent 控制闸门之间的执行路径。
- 左侧一级导航按需求／工作流组织。
- 执行任务位于工作流之下。
- Git 仓库是关联、筛选和交付证据维度，不是默认一级导航。
- 用户界面一级实体命名为“需求”；内部 `projects` 与 `--project` 暂时兼容保留。
- 需求允许关联多个仓库，执行任务关联其中一个或多个仓库子集。
- 初始化需求和多仓库任务前，Agent 必须明确仓库集合；范围不清楚时先向用户确认。

### 第一阶段已实现

- 新增可复用仓库、需求—仓库、任务—仓库关联表；旧 `projects.repo` 自动兼容回填。
- 侧边栏按“需求”组织，并在需求卡和任务节点展示仓库名称标签。
- `board init`、`board set`、`board add`、`board edit` 支持重复 `--repo`。
- 同一仓库匹配多个需求时不再猜测，要求显式传 `-p`。
- taskboard skill 在初始化需求或多仓库任务前要求确认仓库范围。

### 尚待验证

- 多仓库任务完成时，如何采集和展示多个 HEAD、PR 与测试证据。
- finding、risk 和 link 应全部归属工作流，还是允许进一步关联具体任务和仓库。

## 8. 总结

Taskboard 不应只是一个跨项目 TODO 列表，而应成为任务的持久状态和控制面：左侧围绕需要持续推进的工作流组织，中间管理可执行任务，底层关联实际仓库和交付证据。这样 Agent 可以更换、对话可以中断、实现路径可以调整，但目标、结论、风险、闸门和下一步始终有一个可恢复、可检查的去处。
